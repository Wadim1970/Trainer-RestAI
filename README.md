# RestAI Trainer — тренажёр официанта

Отдельный продукт экосистемы RestAI: PWA-приложение, в котором официанты учат меню и стандарты сервиса. Продаётся ресторанам отдельно (курс — на одного официанта).

Это **не часть** приложения официанта (Waiter-app): свой репозиторий, своё приложение, свои аккаунты. Общая только база Supabase (меню, подтверждённые шефом факты о блюдах).

## Как попадает официант

1. Администратор ресторана вносит **email** официанта в админке («Обучение → Доступы») и говорит ему адрес тренажёра.
2. Официант открывает тренажёр, вводит **свой email** — сервер сверяет его со списком — и получает на почту код.
3. Вводит код → попадает в тренажёр. Всякий раз вход такой же: email и код из письма.

**1 email = 1 официант = 1 оплаченное место на один курс.** Администратор может закрыть доступ в любой момент (прогресс сохраняется). Если почты нет в списке или доступ закрыт, после ввода кода показывается понятная причина. Экран кода открывается для любой почты одинаково, чтобы по ответу нельзя было угадывать, кто есть в списке. Когда появятся все уровни и голос, доступ будет закрываться по завершении курса и официанту с администратором уйдёт итоговый отчёт.

## Принципы

- **Вердикт по фактам выносит только код.** Верность ответа — сравнение выбранного с заранее известным набором; ИИ в этих упражнениях не участвует.
- **В тренажёр попадают только подтверждённые шефом факты** (контент-студия в Admin-restai, таблица `trn_dish_facts`). Нет подтверждённого состава — блюдо недоступно на уровне 2, и тренажёр честно говорит «шеф ещё не подтвердил данные».
- **Сервер хранит вопросы и верные ответы** (`trn_sessions`) и сам проверяет присланное; повторная отправка тех же ответов не удваивает баллы.
- **Пороги, веса и лимиты — настройки ресторана** (`trn_settings`), а не константы: баллы для открытия уровня, карточек в день, длина сессии, вес ответов, комбо. Умолчания — `api/_lib/settingsCore.js`.
- **Данные других клиентов в обучении не используются.** Неправильные варианты («Цезарь с креветками») строятся подменой основного продукта в названии и из обезличенного каталога типовых блюд.
- **Ингредиент, упомянутый в названии или описании блюда, никогда не станет «лишним»** — даже если шеф внёс состав не полностью.

## Структура

```
api/                      функции API (формат Vercel; на сервере запускаются deploy/api-server.mjs из RestAI как есть)
  me.js session.js answers.js        — для официанта (Authorization: Bearer <сессия Supabase>)
  admin/enrollments.js               — доступы официантов (для администратора ресторана)
  _lib/*Core.js                      — чистая логика (без БД и сети), покрыта тестами
  _lib/*Service.js                   — ввод-вывод
src/                      PWA (React + Vite + TypeScript, vite-plugin-pwa)
supabase/migrations/      миграции общей БД (+ откат к каждой)
```

## Запуск

```bash
npm install
cp .env.example .env        # заполнить значения
npm run dev                 # фронтенд
npm test                    # тесты API (node:test)
npm run build               # сборка PWA
```

API запускается как у остальных продуктов RestAI: `deploy/api-server.mjs --dir <папка этого репозитория> --port <порт>`; nginx отдаёт `/api/` этому процессу. Переменные окружения — `.env.production` в папке репозитория (формат — `.env.example`).

> Пошаговый запуск на серверах (почта, миграции, переменные, nginx, проверка) — **[docs/DEPLOY.md](docs/DEPLOY.md)**.

## Требования к Supabase (проверьте до запуска)

1. **Миграции** (из-под `supabase_admin`, по порядку):
   1. `RestAI/supabase/migrations/20261101020000_trainer_facts.sql` — факты о блюдах (контент-студия);
   2. `supabase/migrations/20261101030000_trainer_core.sql` — таблицы тренажёра;
   3. `supabase/migrations/20261106010000_trainer_enrollments.sql` — доступы официантов по email.
2. **Отправка почты (SMTP) в GoTrue должна быть настроена.** Код из письма отправляет сам Supabase Auth; без SMTP письма не уйдут, и никто не сможет ни зарегистрироваться, ни войти. В репозиториях RestAI/Waiter-app/Admin-restai отправки почты нет, настроен ли SMTP на вашем сервере — неизвестно.
3. **Шаблон письма «Magic Link / OTP» должен содержать `{{ .Token }}`** (код), а не только ссылку. Длина кода по умолчанию — 6 цифр (`GOTRUE_MAILER_OTP_LENGTH`).
4. **Пользователей для входа заводит сервер** (админ-API Supabase Auth, когда администратор вносит email), поэтому регистрацию по email в GoTrue включать не нужно. Доступ даёт только запись в списке доступов.
5. В `waiter-api`/GoTrue для нового домена приложения добавьте его в разрешённые адреса (`CORS_ORIGIN`, `GOTRUE_URI_ALLOW_LIST` при необходимости).

## Ограничения, которые нужно знать

- **Вход администратора — тестовый.** Управление доступами защищено так же, как админка Waiter-app: учебный ресторан («Сыроварня») открыт без входа, остальные — общим токеном `ADMIN_TOKEN` в заголовке `X-Admin-Token`. Токен нельзя отдавать в браузер администратора ресторана. Заменить на настоящий вход для администраторов до подключения реальных клиентов.
- **Запись ответа и обновление повторения — несколько отдельных запросов** к базе (не одна транзакция). При обрыве между ними повторная отправка не удвоит баллы, но расписание повторений по этой карточке может не обновиться. Если это станет заметно — перенести в SQL-функцию.
- **Офлайн:** оболочка приложения и главный экран работают без сети, ответы копятся в очереди и уходят при появлении связи. Сама сессия выдаётся сервером, поэтому начать занятие без сети нельзя (после начала — можно закончить).
- **Размер сборки:** основной бандл около 500 КБ из-за клиента Supabase; при необходимости ленивая подгрузка.
